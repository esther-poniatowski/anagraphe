# Logical targets specification

This page fixes the readings of a logical target, of the declarations of identifiers and units, and
of the identity of a repository, so that every read side, in Python and in TypeScript, reads them
alike. The readings rest on the published schema resource `addressing.v1`. The [conformance
cases](https://github.com/esther-poniatowski/anagraphe/blob/main/specs/conformance/targets.yml) fix
each reading, the [identity
cases](https://github.com/esther-poniatowski/anagraphe/blob/main/specs/conformance/identity.yml) fix
the derivation of the identity, and the [targets guide](../guide/targets.md) shows the declarations,
the configuration and the findings of the check.

## Resources

The resource `https://github.com/esther-poniatowski/anagraphe/schemas/addressing.v1.schema.yml` is
published as package data, and defines the definitions below under `$defs`:

| Definition | Content |
| --- | --- |
| `repository-id` | the identifier of a repository |
| `record-id` | the identifier of a record, unique within its repository |
| `unit-id` | the identifier of a unit inside a record |
| `contract-entry` | an entry of `x-target-contract`, which names a contract |
| `property-path` | the dotted path of property names that `x-identifier` holds |
| `field-path` | the text naming one node of a document, as the [field-path specification](field-paths.md) states it |
| `field-path-pattern` | a field path that may hold the wildcards `[*]` and `*` |
| `target` | the mapping `{repository, id, unit}`, each key typed by one of the three identifier definitions |

Each definition other than `target` states a pattern, which admits a string only when it matches
the whole string. JSON Schema reads a pattern under ECMA-262, where `$` matches at the end of the
string only, whereas the validator of Python also matches `$` before a final line break.
Therefore, each pattern closes on `$(?!\n)`, an ending read alike by both engines. The resource
is the single source of the patterns: the Python read side compiles them from the packaged file,
and the TypeScript read side generates them from it. The registry of
Anagraphe, `specs/schema-registry.yml`, in the format `kleisis:schema-registry@2`, maps the `$id`
of the resource under `resources`, and the contract `anagraphe:repository@1` of the retired
manifest under `schemas`. That contract stays registered until the files bound to it migrate.

## Reading of a target

A value is a target when it passes five checks, in this order. The first failed check names the
reason of an invalid value:

1. `not-a-mapping`: the value is a mapping;
2. `unknown-key`: the value holds no key other than `repository`, `id` and `unit`;
3. `no-record-or-repository`: the value holds `id`, or `repository`;
4. `unit-without-record`: a mapping holding `unit` also holds `id`;
5. `invalid-component`: each key present holds a string admitted by its definition.

A value is a target exactly when the definition `target` validates it. A target holding
`repository` and no `id` names that repository itself.

## Normalization and equality

The repository holding a citing file is the repository whose root contains the file; a nested
repository, such as a submodule, is a repository of its own. Its identifier is derived as the
section "Identity" states, and it has none when the derivation yields none. The normalization of a
target fills an absent `repository` with that identifier, and leaves it absent when the repository
has no identity.
Two targets are equal when their normalized mappings are equal, each identifier compared case by
case. A document generated by a tool writes the repository of every target, so that its meaning
does not depend on the repository that reads it.

## Target fields

A target field is a field whose schema node holds a `$ref` equal to
`https://github.com/esther-poniatowski/anagraphe/schemas/addressing.v1.schema.yml#/$defs/target`,
compared as an exact string. A read side recognizes the definition by that URI, and does not read
the resource. The schema of the citing record is read through `properties`, `items`,
`additionalProperties`, the subschemas of `allOf`, `anyOf` and `oneOf`, and every other `$ref`. The
key path of the field grows through `properties`, by the name of each property, through `items`, by
every item of an array, and through `additionalProperties`, by every value of a mapping under a key
that the sibling `properties` does not declare. A node reached under another applicator, such as
`not` or `patternProperties`, describes no field.

When every node reaching the definition does so through `anyOf` or `oneOf`, the value matches the
definition only in one branch, so a value of the field is read as a target only when it is a
mapping.

## Contracts of a target field

The keyword `x-target-contract`, on a node of the key path of a target field, holds a non-empty list
of contract identifiers, each `namespace:name` or `namespace:name@n`, as the definition
`contract-entry` admits. An entry `namespace:name`
admits every version of that contract, and an entry `namespace:name@n` admits that version only.
The contracts of a record are its `_schema`, followed by every contract that the root schema of
that `_schema` declares under `x-implements`, as a string or a list of strings, read at the root
through `allOf` and `$ref`. A list admits a record when one entry admits one of its contracts. When
several nodes of the key path declare `x-target-contract`, the record satisfies each declaration.

## Identifiers and units

The keyword `x-identifier` holds a dotted path of property names, as the definition `property-path`
admits, a field path as the [field-path specification](field-paths.md) states. Followed from the key
path of its node, the path names a property that the schema of the contract declares. The keyword is
read on two kinds of node, outside `anyOf` and `oneOf`:

- on the root of the schema of a contract, read through `allOf` and `$ref`, it names the field of
  the identifier of the record; the first declaration in the order of the walk applies;
- on a definition reached as the items of an array, it names the field of the identifier of each
  item, and makes each item a unit of the record.

Without a declaration at the root, the identifier of a record is the key `id` of the metadata
source that the section `metadata` of `anagraphe.yml` declares for its file, the same source from
which the indexes read the fields of the file. The built-in sources read the frontmatter of a
Markdown note, and the key paths `.` then `metadata` of a YAML document. A JSON document has no
built-in source, so it holds a default identifier only under a declared source. A TOML document is
a record when its declared source is `toml`.

A key path of the source holds the identifier when the mapping found at that path holds the key `id`
with a value other than null. The path `.` names the top level, without the key naming the first
segment of a deeper declared path. When several key paths hold `id`, the identifier and its pointer
are those of the first path in the declared order. A later path holding another value is a finding
`invalid-identifier`, located at that later path, and the record keeps the identifier of the first
path. Under the built-in source, a YAML document holding `id: a` and `metadata: {id: b}` is thus
identified as `a`, with a finding at `/metadata/id`.

The units of a record are the identifiers of its declared items, each a `unit-id`, and, in a
Markdown record, the names of its block anchors, each a caret token `^name` closing a line of the
body after a space or a line break, whose name is a `unit-id`. A declared item identifier other
than null that lies outside the pattern `unit-id` is no unit; it is a finding `invalid-identifier`,
located at the field of the item, as for a record identifier. A heading is not a unit. The units of
one record share one namespace, so a unit declared twice is ambiguous. The items of a mapping keyed
by identifier are not units in this version.

## Identity

The identifier of a repository is derived in this order:

1. the override `repository.id` of `anagraphe.yml`, when the configuration declares it;
2. the name of the remote `origin` of the root, when the pattern of `repository-id` admits it. The
   name is the last segment of the address of the remote, after `/` or the `:` of an scp-like
   address, without a final `/` and `.git`. For example, `git@github.com:lab/geonexus.git` and
   `https://github.com/lab/geonexus/` both name `geonexus`;
3. the name of the folder of the root, under the same pattern;
4. otherwise, the repository has no identity.

The former identifiers of the repository are those of `repository.retired` in `anagraphe.yml`. The
section `repository` admits two keys:

| Key | Content |
| --- | --- |
| `repository.id` | the override of the identifier, a `repository-id` |
| `repository.retired` | the former identifiers, each a distinct `repository-id`, and none equal to the identifier |

A section holding another key, or a value outside these constraints, is a configuration error. A
list `repository.retired` holding the derived identifier is a configuration error as well, repaired
by an override. Without an override, a remote name and a folder name that are two different
identifiers raise the warning `identity-disagreement`, and the remote name wins. An override settles
the disagreement, as in a fork, whose remote bears another name than the repository that it
continues.

A selected state of another repository has no folder of its own, so its identity is the override of
the configuration at that state, else the name of its remote.

Until the amendment of [ADR 0006](../adr/0006-logical-targets.md) on 2026-11-19, a repository
declared its identifier in a manifest, `repository.yml` at its root, under `anagraphe:repository@1`.
A `repository.yml` left at the root is reported as `retired-repository-manifest`, stays out of the
records. Its finding names the section `repository` to write when the derived identifier or the
configured former identifiers differ from those of the manifest.

## Versioning

Adding a definition to the resource keeps its `$id`. A change that makes a valid target invalid, or
changes the meaning of a key, publishes `addressing.v2.schema.yml` under a new `$id`, and the file
`v1` stays until no consumer references it. A contract, such as `anagraphe:record-registry@1`,
follows the same rule under a new contract identifier.

Since the `$id` and each contract identifier carry their major version, each read side declares its
implemented versions as a mapping with the keys below:

| Key | Version |
| --- | --- |
| `addressing` | the `$id` of the resource of the addressing |
| `registry` | the contract of the [record registry](record-registry.md), `anagraphe:record-registry@1` |

Until the amendment of [ADR 0006](../adr/0006-logical-targets.md) on 2026-11-19, the mapping also
held the key `repository`, the contract `anagraphe:repository@1` of the retired manifest. Neither
read side reads that contract since the identity of a repository is derived, so the key is
removed.

The Python read side exports the mapping as `anagraphe.targets.IMPLEMENTED_SPECIFICATION`, and the
TypeScript package `@anagraphe/read` exports it as `IMPLEMENTED_SPECIFICATION`. A host bundling the
package writes that mapping into a file of its repository, and `anagraphe targets check` compares
it with the mapping of Anagraphe, as the [targets guide](../guide/targets.md) states.
