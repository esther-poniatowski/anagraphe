# Logical targets specification

This page fixes the readings of a logical target, of the declarations of identifiers and units, and
of the manifest of a repository, so that every read side, in Python and in TypeScript, reads them
alike. The readings rest on two published resources: the schema resource `addressing.v1` and the
contract `anagraphe:repository@1`. The [conformance cases](https://github.com/esther-poniatowski/anagraphe/blob/main/specs/conformance/targets.yml)
fix each reading, and the [targets guide](../guide/targets.md) shows the declarations, the
configuration and the findings of the check.

## Resources

The resource `https://github.com/esther-poniatowski/anagraphe/schemas/addressing.v1.schema.yml` is
published as package data, and defines four definitions under `$defs`:

| Definition | Content |
| --- | --- |
| `repository-id` | the identifier of a repository |
| `record-id` | the identifier of a record, unique within its repository |
| `unit-id` | the identifier of a unit inside a record |
| `target` | the mapping `{repository, id, unit}`, each key typed by one of the definitions above |

Each identifier definition states its pattern, and a pattern admits an identifier only when it
matches the whole string. The resource is the single source of the patterns: the Python read side
compiles them from the packaged file. The registry of
Anagraphe, `specs/schema-registry.yml`, in the format `kleisis:schema-registry@2`, maps the `$id`
of the resource under `resources`, and the contract `anagraphe:repository@1` under `schemas`.

## Reading of a target

A value is a target when it passes five checks, in this order. The first failed check names the
reason of an invalid value:

1. `not-a-mapping`: the value is a mapping;
2. `unknown-key`: the value holds no key other than `repository`, `id` and `unit`;
3. `no-record-or-repository`: the value holds `id`, or `repository`;
4. `unit-without-record`: a mapping holding `unit` also holds `id`;
5. `invalid-component`: each key present holds a string admitted by its definition.

A value is a target exactly when the definition `target` validates it. A target holding
`repository` and no `id` names that repository itself.

## Normalization and equality

The repository holding a citing file is the repository whose root contains the file; a nested
repository, such as a submodule, is a repository of its own. Its identifier is the `repository.id`
of its manifest, and it has none without a valid manifest. The normalization of a target fills an
absent `repository` with that identifier, and leaves it absent when the repository declares none.
Two targets are equal when their normalized mappings are equal, each identifier compared case by
case. A document generated by a tool writes the repository of every target, so that its meaning
does not depend on the repository that reads it.

## Target fields

A target field is a field whose schema node holds a `$ref` equal to
`https://github.com/esther-poniatowski/anagraphe/schemas/addressing.v1.schema.yml#/$defs/target`,
compared as an exact string. A read side recognizes the definition by that URI, and does not read
the resource. The schema of the citing record is read through `properties`, `items`,
`additionalProperties`, the subschemas of `allOf`, `anyOf` and `oneOf`, and every other `$ref`. The
key path of the field grows through `properties`, by the name of each property, through `items`, by
every item of an array, and through `additionalProperties`, by every value of a mapping under a key
that the sibling `properties` does not declare. A node reached under another applicator, such as
`not` or `patternProperties`, describes no field.

When every node reaching the definition does so through `anyOf` or `oneOf`, the value matches the
definition only in one branch, so a value of the field is read as a target only when it is a
mapping.

## Contracts of a target field

The keyword `x-target-contract`, on a node of the key path of a target field, holds a non-empty list
of contract identifiers, each `namespace:name` or `namespace:name@n`. An entry `namespace:name`
admits every version of that contract, and an entry `namespace:name@n` admits that version only.
The contracts of a record are its `_schema`, followed by every contract that the root schema of
that `_schema` declares under `x-implements`, as a string or a list of strings, read at the root
through `allOf` and `$ref`. A list admits a record when one entry admits one of its contracts. When
several nodes of the key path declare `x-target-contract`, the record satisfies each declaration.

## Identifiers and units

The keyword `x-identifier` holds a dotted path of property names, each name matching
`^[A-Za-z_][A-Za-z0-9_-]*$`. Followed from the key path of its node, the path names a property
that the schema of the contract declares. The keyword is read on two kinds of node, outside `anyOf` and
`oneOf`:

- on the root of the schema of a contract, read through `allOf` and `$ref`, it names the field of
  the identifier of the record; the first declaration in the order of the walk applies;
- on a definition reached as the items of an array, it names the field of the identifier of each
  item, and makes each item a unit of the record.

Without a declaration at the root, the identifier of a record is the key `id` of its metadata
source: the frontmatter of a Markdown note, or the block `metadata` of a YAML or JSON document.

The units of a record are the string identifiers of its declared items, and, in a Markdown record,
the names of its block anchors, each a caret token `^name` closing a line of the body after a space
or a line break, whose name is a `unit-id`. A heading is not a unit. The units of one record share one namespace, so a unit
declared twice is ambiguous. The items of a mapping keyed by identifier are not units in this
version.

## Manifest

A repository declares its identifier in `repository.yml` at its root, which follows
`anagraphe:repository@1`:

| Key | Content |
| --- | --- |
| `_schema` | `anagraphe:repository@1` |
| `repository.id` | the identifier of the repository, a `repository-id` |
| `repository.retired` | the former identifiers, each a distinct `repository-id`, and none equal to `repository.id` |

The block `repository` admits no other key, and every other root key is left to other contracts.
During the migration, a manifest written `schema_version: 1`, without `_schema`, is read under the
same contract and reported. A manifest holding both keys, or another version, is invalid, and an
invalid manifest declares no identifier.

## Versioning

Adding a definition to the resource keeps its `$id`. A change that makes a valid target invalid, or
changes the meaning of a key, publishes `addressing.v2.schema.yml` under a new `$id`, and the file
`v1` stays until no consumer references it. The contract `anagraphe:repository@1` follows the same
rule under a new contract identifier.
